This hands-on section deploys the NVIDIA RAG Blueprint `v2.6.0` with Helm. The lab values file keeps model inference on NVIDIA hosted endpoints and uses Elasticsearch as the vector database, which is the default vector store for the `v2.6.0` chart.

## Prerequisites

Before running the deployment commands, make sure this environment variable is available in the lab shell:

`NGC_API_KEY` is required to pull the RAG Helm chart, access NGC container images, and call NVIDIA hosted endpoints.

```bash
env | grep NGC_API_KEY
```

If you do not have a key yet, follow NVIDIA's [Generating NGC API Keys](https://docs.nvidia.com/ngc/latest/ngc-user-guide.html#generating-ngc-api-keys) documentation. You can manage keys from the [NGC API Keys page](https://org.ngc.nvidia.com/account/api-keys).

Open  a new shell and set your NGC_API_KEY

```bash-ref
export NGC_API_KEY="<your-ngc-or-nvidia-api-key>"
```

<Callout type="warn" title="Keep keys private">
Do not paste real keys into shared logs or committed files. The commands below pass the key to Helm so Kubernetes secrets can be created by the chart.
</Callout>

The `v2.6.0` RAG chart also expects Elastic Cloud on Kubernetes (ECK). ECK installs the Elasticsearch custom resources and operator that the chart uses to create the default vector database.

## 1. Install the ECK operator

Add the Elastic Helm repository and install the ECK operator:

```bash
helm repo add elastic https://helm.elastic.co
helm repo update
helm upgrade --install elastic-operator elastic/eck-operator \
  -n elastic-system \
  --create-namespace
```

Wait for the operator to become available:

```bash
kubectl rollout status deployment/elastic-operator \
  -n elastic-system \
  --timeout=180s
```

You should see the ECK operator pod running:

```bash
kubectl get pods -n elastic-system
```

## 2. Create the namespace

Create the namespace if it does not already exist:

```bash
kubectl create namespace rag --dry-run=client -o yaml | kubectl apply -f -
```

This command is rerunnable. If you repeat the lab, Kubernetes keeps the existing namespace and continues.

## 3. Inspect the chart defaults

Start by looking at the upstream chart defaults. This helps you see what the lab override file is changing.

```bash
helm show values https://helm.ngc.nvidia.com/nvidia/blueprint/charts/nvidia-blueprint-rag-v2.6.0.tgz \
  --username '$oauthtoken' \
  --password "$NGC_API_KEY" | sed -n '1,220p'
```


## 4. Inspect the lab values file

This repository includes the custom values used by the launchable:

```bash
cat manifests/rag-values.yaml
```

The important settings are:

- Hosted endpoints: for the RAG `v2.6.0` services, empty model server URL fields mean "use NVIDIA hosted endpoints" instead of in-cluster NIM services. The NV-Ingest runtime is stricter, so the lab sets `EMBEDDING_NIM_ENDPOINT` explicitly to the hosted embeddings base URL.
- RAG `v2.6.0` model names: the lab uses hosted endpoint model names that work with the `v2.6.0` chart configuration: `APP_EMBEDDINGS_MODELNAME` and `EMBEDDING_NIM_MODEL_NAME` use `nvidia/llama-nemotron-embed-vl-1b-v2`, and `APP_RANKING_MODELNAME` uses `nvidia/llama-nemotron-rerank-vl-1b-v2`.
- Local NIM services disabled: the `nimOperator` overrides disable local model-serving pods so the lab does not require GPUs or large model caches.
- Elasticsearch vector database: `eck-elasticsearch.enabled` is set to `true`, `APP_VECTORSTORE_NAME` is set to `elasticsearch`, and `APP_VECTORSTORE_URL` points to the Elasticsearch service that ECK creates in the `rag` namespace.
- CPU vector search path: `APP_VECTORSTORE_ENABLEGPUSEARCH` and `APP_VECTORSTORE_ENABLEGPUINDEX` are set to `False` so the vector database path does not require GPUs.
- Text-focused ingestion: table, chart, image, and infographic extraction are disabled so the launchable can focus on document text ingestion without requiring extraction NIMs.
- Smaller NV-Ingest footprint: the upstream NV-Ingest defaults request much larger resources than this launchable provides. The lab values reduce `nv-ingest.resources`, `MAX_INGEST_PROCESS_WORKERS`, `NV_INGEST_MAX_UTIL`, and `PDF_SPLIT_PAGE_COUNT` for an 8 CPU / 32 GiB VM.
- Secrets are not stored in the file. The API key is passed through Helm flags during installation.

## 5. Install the RAG Blueprint

Install the chart with the lab values file:

```bash
helm upgrade --install rag -n rag \
  https://helm.ngc.nvidia.com/nvidia/blueprint/charts/nvidia-blueprint-rag-v2.6.0.tgz \
  --username '$oauthtoken' \
  --password "$NGC_API_KEY" \
  --set imagePullSecret.password="$NGC_API_KEY" \
  --set ngcApiSecret.password="$NGC_API_KEY" \
  -f manifests/rag-values.yaml \
  --wait --timeout 20m
```

## 6. Validate the deployment

Check that all pods are running:

```bash
kubectl get pods -n rag
```

Expected shape:

```text
rag-server-...                         1/1 Running
ingestor-server-...                    1/1 Running
rag-frontend-...                       1/1 Running
rag-nv-ingest-...                      1/1 Running
rag-eck-elasticsearch-es-default-0     1/1 Running
rag-redis-...                          1/1 Running
```

Verify the k8s services:

```bash
kubectl get svc -n rag
```

The services AI-Q will use later are:

- `rag-server` on port `8081`
- `ingestor-server` on port `8082`
- `rag-frontend` on port `3000`, exposed through Envoy at `/rag`
- `rag-eck-elasticsearch-es-default` on port `9200`, used internally as the vector database


Verify the Envoy route:

```bash
kubectl get httproute -n rag rag-frontend
```

You can also run direct health checks from inside the cluster. 

Start a temporary curl pod to check the RAG server:


```bash
kubectl run rag-healthcheck -n rag --quiet --rm -i --restart=Never \
  --image=curlimages/curl:8.10.1 -- \
  curl -sf http://rag-server:8081/health | jq
```

Then check the ingestor server:

```bash
kubectl run rag-ingestor-healthcheck -n rag --quiet --rm -i --restart=Never \
  --image=curlimages/curl:8.10.1 -- \
  curl -sf http://ingestor-server:8082/health | jq
```

Expected result: each endpoint returns HTTP `200` or a successful health response.

## 8. Troubleshoot

If a pod is not ready, inspect events and logs:

```bash
kubectl get events -n rag --sort-by='.lastTimestamp'
```

For `Pending` pods, describe the pod and look at the scheduler message:

```bash
kubectl describe pod -n rag <pending-pod-name>
```

If you see `Insufficient cpu` or `Insufficient memory` for `rag-nv-ingest`, the chart might be using resource requests that are too large for the launchable. Confirm the rendered values:

```bash
helm get values rag -n rag --all | grep -nE "nv-ingest:|resources:|MAX_INGEST_PROCESS_WORKERS|NV_INGEST_MAX_UTIL|PDF_SPLIT_PAGE_COUNT" -A12 -B2
```

If Elasticsearch pods are not created or stay unhealthy, check that ECK is installed and that the Elasticsearch custom resource exists:

```bash
kubectl get pods -n elastic-system
kubectl get elasticsearch -n rag
kubectl describe elasticsearch -n rag
```

To trace requests, you can look at the rag-server logs

```bash
kubectl logs -n rag deploy/rag-server --since=10m
```

To debug issues with ingestion, you can look at the rag-nv-ingest logs

```bash
kubectl logs -n rag deploy/rag-nv-ingest --since=10m
```
