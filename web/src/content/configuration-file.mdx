AI-Q is configured through a YAML file that defines runtime settings, model endpoints, tools, agents, and the top-level workflow. In the earlier deployment sections, `CONFIG_FILE` pointed to config files already packaged inside the backend image. In this section, you will mount a local config file into the backend pod and make AI-Q use it.

Source references: [AI-Q Configuration Reference](https://docs.nvidia.com/aiq-blueprint/2.1.0/customization/configuration-reference.html) and the AI-Q `release/2.1` [config_web_frag.yml](https://github.com/NVIDIA-AI-Blueprints/aiq/blob/release/2.1/configs/config_web_frag.yml).

## 1. Inspect the custom config file

This repository includes a local custom config:

```bash
cat manifests/configs/config_lab_custom.yml
```


The file follows the same top-level structure as the AI-Q configuration reference and builds on the FRAG configuration used in the previous section:

This configuration is based on the AI-Q `release/2.1` `configs/config_web_frag.yml`. It keeps the same major sections, and changes selected values so you can see how a local config override works.

- `general`: logging, telemetry, API frontend, CORS, and runtime settings.
- `llms`: model definitions, model names, hosted endpoint URLs, retry limits, and sampling settings.
- `functions`: data-source registry entries, tools, and agents, including knowledge retrieval, intent classification, shallow research, clarification, and deep research.
- `workflow`: the top-level AI-Q orchestrator and the agents it wires together.

The custom values are grouped by the part of AI-Q they affect.

### Customize logging level
`general.telemetry.logging.console.level` is set to `DEBUG`. This demonstrates how runtime logging can be changed from a mounted config file.

```yaml
general:
  telemetry:
    logging:
      console:
        level: DEBUG
```


### Customize Data sources
`data_sources.sources` contains only `knowledge_layer`. 

The `web_search` source is intentionally removed from the registry, so the UI no longer shows Web Search as a selectable data source.

```yaml
  data_sources:
    _type: data_source_registry
    sources:
      - id: knowledge_layer
        name: "Knowledge Base"
        description: "Search uploaded documents and files."
        default_enabled: true
        tools:
          - knowledge_search
```
This customization is visible from the UI in the lab. The data-source registry is what the UI uses to render source toggles, so changing the registry changes the list of sources the student can select.

### Customize Knowledge layer

`knowledge_search.backend` remains `foundational_rag`, so this custom config still uses the RAG Blueprint deployed earlier.
```
  knowledge_search:
    _type: knowledge_retrieval
    backend: foundational_rag
    top_k: 2
```
`knowledge_search.top_k` is reduced to `2`. This is still relevant because Knowledge Base remains the active source: it controls how many retrieved chunks AI-Q asks the Knowledge Layer to return for a document-grounded request.

### Customize Clarifier agent

```yaml
clarifier_agent:
    max_turns: 1
    enable_plan_approval: false
```
`clarifier_agent.max_turns` is reduced to `1`, which limits how many clarification turns AI-Q can use before continuing.

The clarifier section also exposes human-in-the-loop behavior through `enable_plan_approval`. This lab sets `enable_plan_approval: false`, to avoid asking the user to approve the plan before continuing.

### Customize shallow research agent

```yaml
  shallow_research_agent:
    max_llm_turns: 6
    max_tool_iterations: 4
```
`max_tool_iterations` is reduced to `4`, and `max_llm_turns` is reduced to `6`. These values keep the shallow research path bounded for the lab environment.

The practical impact is that AI-Q starts in a document-focused posture: Knowledge Base is the only data source exposed to the UI, RAG retrieval returns fewer chunks, and shallow research has a smaller iteration budget.



## 2. Inspect the config mount values file

The Helm override file does not contain the whole config. It tells the chart to mount the ConfigMap through `fusionConfig`, then points the backend `CONFIG_FILE` environment variable at the mounted file:

```bash
cat manifests/aiq-custom-config-values.yaml
```

The important values are:

```yaml
aiq:
  fusionConfig:
    enabled: true
    volumeName: aiq-custom-config
    mountPath: /app/custom-config
    configMapName: aiq-custom-config
  apps:
    backend:
      env:
        CONFIG_FILE: /app/custom-config/config_lab_custom.yml
```

That path must exist inside the backend container after the ConfigMap is mounted.

Use `fusionConfig` for this chart instead of overriding `apps.backend.volumeMounts` or `apps.backend.volumes` directly. The chart already defines volumes and mounts for other parts of the deployment, including PostgreSQL initialization. Replacing those lists can produce errors such as `volumeMounts[0].name: Not found: "postgres-init"`.

This values file only changes where `CONFIG_FILE` points and how the file is mounted; it does not define `RAG_SERVER_URL`, `RAG_INGEST_URL`, or `COLLECTION_NAME`. Those still come from `manifests/aiq-frag-values.yaml`, so the Helm upgrade below must include both files.

## 3. Create the ConfigMap

Create or update a ConfigMap from the local config file:

```bash
kubectl create configmap aiq-custom-config -n ns-aiq \
  --from-file=config_lab_custom.yml=manifests/configs/config_lab_custom.yml \
  --dry-run=client -o yaml | kubectl apply -f -
```

ConfigMap updates do not automatically restart an already-running pod. After changing the file, rerun the Helm upgrade in the next step or restart the backend deployment so the pod reads the latest mounted content.

Confirm it exists:

```bash
kubectl get configmap aiq-custom-config -n ns-aiq
```

## 4. Upgrade AI-Q with the custom config

Apply the base AI-Q values, the FRAG environment values, and the custom config mount values:

```bash
helm upgrade --install aiq ./aiq2-web-2.1.0.tgz \
  -n ns-aiq \
  --wait --timeout 10m \
  -f manifests/aiq-values.yaml \
  -f manifests/aiq-frag-values.yaml \
  -f manifests/aiq-custom-config-values.yaml
```

The order matters. `manifests/aiq-frag-values.yaml` keeps the RAG URLs and collection name, while `manifests/aiq-custom-config-values.yaml` enables `fusionConfig`, mounts the ConfigMap, and overrides only backend `CONFIG_FILE`.

Wait for the backend rollout:

```bash
kubectl rollout status deployment/aiq-backend -n ns-aiq --timeout=5m
```

## 5. Verify the mounted config

Check that the backend sees the custom `CONFIG_FILE` path:

```bash
kubectl get deploy aiq-backend -n ns-aiq \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="backend")].env[?(@.name=="CONFIG_FILE")].value}{"\n"}'
```

Expected output:

```text
/app/custom-config/config_lab_custom.yml
```

You can also inspect the rendered deployment to verify the environment variable, `fusionConfig` volume mount, and ConfigMap volume:

```bash
kubectl get deploy aiq-backend -n ns-aiq -o yaml | grep -nE "CONFIG_FILE|aiq-custom-config|custom-config" -A4 -B4
```

## 6. Test the change on Data sources

Confirm that the backend now advertises only the Knowledge Base data source:

```bash

  --image=curlimages/curl:8.10.1 -- \
  sh -c 'curl -s http://aiq-backend:8000/v1/data_sources; echo' | jq .
```

Expected shape:

```json
  {
```

Open the AI-Q UI from the Brev exposed-port link for Envoy with the `/aiq` path.

Open **Data Sources** and notice the custom registry behavior: **Knowledge Base** is shown, and **Web Search** is not shown. That is the visible proof that the custom config changed the list of data sources exposed to the UI.

Upload a file through the **Files** tab, then send a document-grounded prompt:

```text
Using the uploaded document, create a summarizing report
```

This is a good test because it exercises the same FRAG path from the previous section while using the locally mounted config. The smaller `knowledge_search.top_k` should keep retrieval focused, and the reduced shallow research limits make the workflow easier to observe in the lab.

Since approving the plan was disabled, the report creation starts immediately without human-in-the-loop. 

Check the backend logs for the request path:

```bash
kubectl logs -n ns-aiq deploy/aiq-backend --since=10m | grep -Ei "config_lab_custom|shallow_research_agent|intent_classifier|knowledge|rag|retriev|collection"
```

Useful keywords to look for:

- `config_lab_custom`, confirming the mounted config path appears in startup or error logs.
- `intent_classifier`, showing the request passed through classification.
- `shallow_research_agent`, showing the shallow route was selected.
- `knowledge`, `rag`, `retriev`, or `collection`, showing the Knowledge Base path was used.


## 8. Troubleshoot

If the pod does not start, inspect the backend logs without filtering:

```bash
kubectl logs -n ns-aiq deploy/aiq-backend --since=10m
```

Most startup failures in this section are caused by YAML indentation, a missing ConfigMap, a `CONFIG_FILE` path that does not match the mounted file path, or a custom config copied from a different AI-Q release than the backend image you are running.
